# راهنمای عملیات روزانه

## شروع شیفت

- Dashboard، alertها، health کیف‌پول/node، sync height و فضای دیسک را بررسی کنید.
- reject rate، hashrate پنجره‌های 1/5/15 دقیقه و upstream فعال هر worker را با روز قبل مقایسه کنید.
- shareهای `UNKNOWN` را بررسی کنید؛ این shareها خودکار تسویه نمی‌شوند.
- depositهای جدید باید txid/outputRef یکتا، confirmation کافی و وضعیت `ALLOCATED` داشته باشند.

## تسویه

Scheduler با policy قابل‌تغییر پنل اجرا می‌شود. حالت پیش‌فرض `DAILY` در 00:15 Asia/Tehran است و حالت `INTERVAL` از ۶۰ تا ۱۰٬۰۸۰ دقیقه پشتیبانی می‌کند. اجرای interval برای مشتریان، برنامه روزانه/هفتگی برداشت مالک را تغییر نمی‌دهد. walletها دائماً برای reorg و deposit پایش می‌شوند، اما فقط پول واقعاً دریافت‌شده و تأییدشده در موجودی قابل‌پرداخت قرار می‌گیرد؛ shareهای پذیرفته‌شده‌ای که upstream هنوز بابت آن‌ها پول نفرستاده جداگانه به‌عنوان pending work نمایش داده می‌شوند.

برای تلاش تسویه هر ۴ یا ۶ ساعت، در Settings حالت `INTERVAL` و به‌ترتیب `240` یا `360` دقیقه را انتخاب کنید. این زمان، موعد اجرای scheduler است نه تضمین واریز: مشتری فقط وقتی وارد batch می‌شود که deposit تأییدشده، مقصد فعال، حداقل مؤثر و محدودیت‌های policy را داشته باشد. پرتال زمان اجرای بعدی را دقیق و همراه شمارش معکوس نمایش می‌دهد.

تمام مشتریان واجد شرایط در یک تراکنش batch می‌شوند. حداقل سراسری هر asset، حداقل انتخابی مقصد، حداکثر تعداد اعضای batch، پرداخت‌کننده کارمزد و حداکثر نسبت fee همگی از پنل قابل تغییرند. حداقل مؤثر برابر مقدار بزرگ‌ترِ حداقل سراسری و حداقل مقصد است. سقف auto پیش‌فرض صفر است و به‌صورت تجمعی در روز محلی محاسبه می‌شود؛ تقسیم یک مبلغ به چند اجرای ساعتی سقف روزانه را دور نمی‌زند. batch بالاتر از سقف در `APPROVAL_REQUIRED` می‌ماند تا Owner با TOTP تأیید کند.

اگر `feePayer=OPERATOR` باشد، مشتری مبلغ gross را کامل دریافت می‌کند و network fee به هزینه اپراتور ثبت می‌شود. اگر `feePayer=CUSTOMER` باشد، fee متناسب با مبلغ بین خروجی‌ها تقسیم می‌شود. عبور fee از `maxFeeBps` پیش از broadcast، batch را fail-closed متوقف می‌کند. batchهای `FAILED` تا retry و تعیین تکلیف، موجودی را رزرو نگه می‌دارند تا payout موازی ساخته نشود.

پیش از approval آدرس‌ها، gross/net، fee، موجودی wallet و عدم وجود alert reorg را بررسی کنید. پس از `SIGNED` قطع برنامه امن است؛ restart ابتدا txid را در wallet جست‌وجو می‌کند. هرگز برای خطای مبهم یک payout دستی موازی نسازید.

حالت سهم مالک:

- `RETAIN`: درآمد مالک در treasury باقی می‌ماند.
- `MANUAL`: دکمه برداشت مالک batch می‌سازد.
- `DAILY`: در اجرای روزانه batch می‌سازد.
- `WEEKLY`: فقط weekday تنظیمی (Luxon: دوشنبه=1 تا یکشنبه=7) batch می‌سازد.

تغییر آدرس 24 ساعت pending است. مقادیر بالاتر از سقف به approval اجباری می‌روند.

## پرتال مشتری

پرتال روی `/portal` قرار دارد. از صفحه Customers برای هر مشتری یک access code قوی بسازید؛ code فقط همان یک بار نمایش داده می‌شود، در پایگاه داده به‌صورت Argon2 hash ذخیره می‌شود و با rotate کردن، مقدار قبلی فوراً باطل می‌شود. access code را جدا از token اتصال miner و از کانال امن تحویل دهید. آن را در URL، ticket یا log قرار ندهید.

مشتری با slug و access code این موارد را می‌بیند: hashrate بازه‌های ۱/۵/۱۵ دقیقه، shareهای پذیرفته/ردشده، درآمد تخصیص‌یافته واقعی ۲۴ ساعت و ۷ روز، تخمین ۲۴ ساعت بعد بر پایه عملکرد واقعی اخیر، موجودی تأییدشده/رزروشده/قابل‌پرداخت، pending work، حداقل مؤثر، وضعیت واجدشرایط بودن، زمان اجرای بعدی و تاریخچه payout. تخمین درآمد تضمین نیست و تا deposit واقعی upstream در ledger ثبت نشود موجودی قابل برداشت ایجاد نمی‌کند.

مشتری می‌تواند مقصد BTC/XMR و حداقل پرداخت خود را ثبت کند. آدرس با wallet adapter همان شبکه اعتبارسنجی، در خروجی mask، در audit ثبت و با alert عملیاتی همراه می‌شود. مقصد جدید ۲۴ ساعت `PENDING` می‌ماند و سپس جای مقصد فعال را می‌گیرد؛ در این فاصله اپراتور باید alert را بررسی کند. API پرتال برای هر IP محدودیت درخواست دارد، اما rate limit جای access code یکتا و TLS معتبر را نمی‌گیرد.

## خاموش‌کردن

ابتدا اتصال ورودی miner را در firewall ببندید، منتظر resolution درخواست‌های جاری بمانید، Nest را stop و سپس node/Compose را خاموش کنید. PostgreSQL را قبل از backup اجباری kill نکنید. پس از restart، readiness، payoutهای `SIGNED/BROADCAST/FAILED` و shareهای `UNKNOWN` را بررسی کنید.
